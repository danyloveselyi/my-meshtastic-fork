## Критические недостающие элементы

### 1. Детальная реализация getMainFS()

**Проблема**: План упоминает функцию, но не описывает как ее реализовать.

**Что нужно:**
```cpp
// Вариант A: если можно получить lfs_t* из InternalFS
lfs_t* getMainFS() {
    // Как получить lfs_t* из InternalFS?
    // Нужно проверить framework исходники
}

// Вариант B: если создаем свой instance
lfs_t* getMainFS() {
    if (!main_fs_initialized) {
        initMainFS();
    }
    return &main_lfs;
}
```

### 2. Адаптация loadProto/saveProto

**Проблема**: ExtendedFilesystemModule::loadProto() проверяет isNodeDBFile() и использует Extended FS для nodes.proto. После миграции это не нужно.

**Что нужно:**
- Убрать проверку isNodeDBFile()
- Все файлы (включая nodes.proto) должны использовать FSCom (Main FS)
- Упростить логику: убрать ветвление Extended FS vs Main FS

### 3. Обновление isAvailable()

**Проблема**: ExtendedFilesystemModule::isAvailable() проверяет Extended FS. Нужна новая проверка для Main FS.

**Что нужно:**
```cpp
bool isMainFSAvailable() {
    // Проверить что Main FS инициализирован и смонтирован
    // Если используем FSCom: проверить что FSCom.begin() успешно
    // Если используем свой instance: проверить main_fs_initialized && main_fs_mounted
}
```

### 4. Порядок инициализации

**Проблема**: План не описывает точный порядок вызовов при старте.

**Что нужно:**
```
1. preFSBegin() - если нужен
2. FSBegin() или initMainFS() - инициализация Main FS
3. Создание директорий /nodes и /prefs
4. Инициализация NodeDBPersistentBackend
5. Загрузка nodes.proto из Main FS
```

### 5. Обработка ошибок

**Проблема**: План не описывает что делать при ошибках инициализации.

**Что нужно:**
- Если Main FS не инициализировался: fallback на стандартный режим (без NodeDBPersistentBackend)
- Если директории не создались: попробовать создать при первой записи
- Если форматирование не удалось: логировать ошибку и продолжить
