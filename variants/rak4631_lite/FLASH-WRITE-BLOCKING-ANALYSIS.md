# Анализ блокировок при записи flash и влияние на прием пакетов LoRa

## Дата анализа: 2025-01-XX

## Критическая информация из документации SoftDevice

### Из `nrf_soc.h` (строки 890-894):

```cpp
* @note
*      - This call takes control over the radio and the CPU during flash erase and write 
*        to make sure that they will not interfere with the flash access. This means that 
*        all interrupts will be blocked for a predictable time (depending on the NVMC 
*        specification in the device's Product Specification and the command parameters).
```

**КРИТИЧНО:** `sd_flash_write` **БЛОКИРУЕТ все interrupts** во время физической записи flash!

---

## Как работает запись flash

### 1. Асинхронная операция (когда SoftDevice включен)

**Процесс:**
1. Вызов `sd_flash_write()` - функция возвращается **сразу** (не блокирует)
2. SoftDevice инициирует физическую запись flash в фоне
3. **Во время физической записи (1-2ms на слово):**
   - Все interrupts **БЛОКИРУЮТСЯ**
   - Radio (BLE) **БЛОКИРУЕТСЯ**
   - CPU **БЛОКИРУЕТСЯ** для других операций
4. После завершения записи:
   - SoftDevice отправляет событие `NRF_EVT_FLASH_OPERATION_SUCCESS`
   - Interrupts разблокируются
   - Система продолжает работу

### 2. Синхронная операция (когда SoftDevice выключен)

**Процесс:**
1. Вызов `sd_flash_write()` - функция **блокирует** до завершения записи
2. Во время записи все interrupts блокируются
3. После завершения функция возвращается

---

## Влияние на прием пакетов LoRa

### ✅ ХОРОШИЕ НОВОСТИ:

1. **Extended FS НЕ использует `spiLock`:**
   - Extended FS использует SoftDevice API напрямую, не SPI
   - LoRa использует SPI и `spiLock` для защиты SPI bus
   - **НЕТ конфликта** между Extended FS и LoRa на уровне SPI

2. **Операция асинхронная:**
   - После вызова `sd_flash_write()` функция возвращается сразу
   - Физическая запись происходит в фоне
   - Основной поток не блокируется

3. **Пакетная запись уменьшает количество блокировок:**
   - Вместо 1024 блокировок по 1-2ms каждая
   - Теперь 1-4 блокировки по 256-1024ms каждая
   - **Меньше прерываний** приема пакетов

### ⚠️ ПРОБЛЕМЫ:

1. **Interrupts блокируются во время физической записи:**
   - LoRa использует hardware interrupts (ISR) для приема пакетов
   - ISR вызывается когда пакет приходит (`isrRxLevel0()`)
   - Если interrupts заблокированы во время записи flash, **пакет может быть потерян**

2. **Время блокировки:**
   - **Старая реализация:** 1024 блокировки × 1-2ms = **1-2 секунды** блокировки
   - **Новая реализация (пакетная):** 1-4 блокировки × 256-1024ms = **256-4096ms** блокировки
   - **Проблема:** Пакетная запись создает **более длительные** блокировки!

3. **Цикл ожидания с `delay(1)`:**
   - В коде используется `delay(1)` в цикле ожидания завершения записи
   - `delay()` может блокировать обработку interrupts
   - Но это менее критично, так как interrupts уже заблокированы во время физической записи

## Детальный анализ блокировок

### Текущая реализация (пакетная запись):

```cpp
// Запись батча 256 слов (1KB)
sd_flash_write(write_addr, src_words, 256);  // Блокирует interrupts на ~256-512ms

// Ожидание завершения
while (!success && elapsed < timeout) {
    delay(1);  // Может блокировать interrupts
    // Проверка flash каждые 2-5ms
}
```

**Время блокировки interrupts:**
- Физическая запись: **256-512ms** (256 слов × 1-2ms)
- Цикл ожидания: **2-5ms** (проверка flash)
- **Общее время блокировки: ~258-517ms на батч**

**Для файла 4KB (4 батча):**
- Общее время блокировки: **1-2 секунды**
- Количество блокировок: **4 раза**

### Старая реализация (по одному слову):

```cpp
// Запись одного слова
sd_flash_write(write_addr, &word, 1);  // Блокирует interrupts на ~1-2ms

// Ожидание завершения
while (!success && elapsed < timeout) {
    delay(1);  // Может блокировать interrupts
    // Проверка flash каждые 2-5ms
}
```

**Время блокировки interrupts:**
- Физическая запись: **1-2ms** (1 слово)
- Цикл ожидания: **2-5ms** (проверка flash)
- **Общее время блокировки: ~3-7ms на слово**

**Для файла 4KB (1024 слова):**
- Общее время блокировки: **3-7 секунд** (но распределено на 1024 коротких блокировки)
- Количество блокировок: **1024 раза**

## Сравнение подходов

| Параметр | Старая (1 слово) | Новая (256 слов) |
|----------|------------------|-----------------|
| Время блокировки на операцию | 3-7ms | 258-517ms |
| Количество блокировок (4KB) | 1024 | 4 |
| Общее время блокировки | 3-7 секунд | 1-2 секунды |
| Вероятность потери пакета | Низкая (короткие блокировки) | **Высокая (длинные блокировки)** |
| Общее время записи | 2-3 секунды | 10-50ms |

### Вывод:

**Пакетная запись быстрее, но создает более длительные блокировки interrupts!**

## Рекомендации по оптимизации

### ✅ Уже реализовано:

1. **Пакетная запись:**
   - Сокращает общее время записи
   - Уменьшает количество блокировок
   - Но увеличивает длительность каждой блокировки

2. **Ранняя проверка flash:**
   - Проверка через 2ms вместо ожидания события
   - Сокращает время ожидания

### 💡 Возможные улучшения:

#### 1. Уменьшить размер батча (КРИТИЧНО для приема пакетов)

**Проблема:** Батч 256 слов блокирует interrupts на 256-512ms

**Решение:** Использовать меньший батч (64-128 слов)
- Блокировка interrupts: **64-256ms** вместо 256-512ms
- Количество блокировок: **8-16** вместо 4
- Общее время блокировки: **512-4096ms** (но распределено)
- **Вероятность потери пакета: СНИЖЕНА**

**Реализация:**
```cpp
constexpr uint32_t OPTIMAL_BATCH_SIZE = 64;  // Уменьшено с 256 до 64
// Блокировка interrupts: 64-128ms вместо 256-512ms
```

#### 2. Использовать `yield()` вместо `delay(1)`

**Проблема:** `delay(1)` может блокировать обработку interrupts

**Решение:** Использовать `yield()` или FreeRTOS `taskYIELD()`
- Позволяет другим задачам выполняться
- Может помочь обработать pending interrupts

**Реализация:**
```cpp
// Вместо:
delay(1);

// Использовать:
yield();  // Или taskYIELD() для FreeRTOS
```

#### 3. Проверять pending interrupts перед записью

**Проблема:** Запись может начаться во время обработки пакета LoRa

**Решение:** Проверять, нет ли pending interrupts перед записью
- Если есть pending interrupts, отложить запись
- Или использовать более короткий батч

**Реализация:**
```cpp
// Проверить pending interrupts перед записью
if (hasPendingLoRaInterrupts()) {
    // Использовать меньший батч или отложить запись
    words_to_write = 32;  // Минимальный батч
}
```

#### 4. Разбить большую запись на несколько маленьких

**Проблема:** Запись 4KB блокирует interrupts на 1-2 секунды

**Решение:** Разбить запись на части с паузами между ними
- Записать 64 слова → пауза 10ms → записать 64 слова → ...
- Позволяет обработать pending interrupts между батчами

**Реализация:**
```cpp
while (i < size) {
    // Записать батч
    sd_flash_write(...);
    // Подождать завершения
    wait_for_completion();
    
    // ПАУЗА для обработки interrupts
    delay(10);  // Позволяет обработать pending interrupts
    
    // Следующий батч
    i += batch_size_bytes;
}
```

## Выводы

### Текущее состояние:

- ✅ **Extended FS НЕ блокирует SPI bus** (не использует `spiLock`)
- ✅ **Операция асинхронная** (не блокирует основной поток)
- ⚠️ **Interrupts блокируются** во время физической записи flash
- ⚠️ **Пакетная запись создает длительные блокировки** (256-512ms)

### Влияние на прием пакетов:

- **Короткие блокировки (1-2ms):** Пакеты могут быть потеряны, но вероятность низкая
- **Длинные блокировки (256-512ms):** **ВЫСОКАЯ вероятность потери пакетов!**

### Рекомендация:

**Уменьшить размер батча до 64 слов** для снижения вероятности потери пакетов, даже если это немного увеличит общее время записи.
