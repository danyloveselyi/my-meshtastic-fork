# Анализ производительности файловой системы

## Дата анализа: 2025-01-XX

## Сравнение: Стандартная vs Extended Filesystem

### Стандартная файловая система (Main FS, 7 pages, 28 KB)

**Используется для:** `config.proto`, `device.proto`, `module.proto`, `channels.proto`, `uiconfig.proto`

**Архитектура:**
- **Wrapper:** Adafruit LittleFS (через `InternalFS`)
- **API:** Высокоуровневый (`File`, `SafeFile`)
- **Блокировка:** `spiLock` (для SPI bus - LoRa radio + filesystem)
- **Запись:** Потоковая через `writecb` callback
- **Кодирование:** Protobuf кодируется напрямую в файл (stream-based)

**Процесс записи:**
1. `SafeFile::SafeFile()` - открывает файл (с `spiLock`)
2. `pb_encode()` с `writecb` - кодирует protobuf и пишет напрямую в файл
3. Каждый байт проходит через `writecb` → `SafeFile::write()` → `File::write()` → LittleFS
4. `SafeFile::close()` - закрывает файл (с `spiLock`)

**Производительность:**
- ✅ **Плюсы:**
  - Потоковая запись (не требует большого буфера в RAM)
  - Оптимизированный Adafruit wrapper
  - Кэширование на уровне LittleFS
- ⚠️ **Минусы:**
  - `spiLock` блокирует SPI bus (может конфликтовать с LoRa radio)
  - Множественные вызовы `writecb` (overhead на каждый байт)
  - Проверка hash при каждом write (XOR для каждого байта)

---

### Extended файловая система (80 pages, 320 KB)

**Используется для:** `nodes.proto` (только другие ноды из сети)

**Архитектура:**
- **Wrapper:** Прямые вызовы LittleFS API (без Adafruit wrapper)
- **API:** Низкоуровневый (`lfs_file_open`, `lfs_file_write`, `lfs_file_close`)
- **Блокировка:** НЕТ `spiLock` (использует SoftDevice API напрямую, не SPI)
- **Запись:** Буферная (encode в буфер, затем запись буфера)
- **Кодирование:** Protobuf кодируется в RAM буфер, затем буфер пишется в файл

**Процесс записи:**
1. `lfs_remove()` - удаляет старый файл
2. `lfs_file_open()` - открывает файл для записи
3. `malloc()` - выделяет буфер в RAM
4. `pb_encode()` в буфер - кодирует protobuf в RAM
5. `lfs_file_write()` - пишет весь буфер одним вызовом
6. `lfs_file_sync()` - синхронизирует файл
7. `lfs_file_close()` - закрывает файл
8. `free()` - освобождает буфер

**Производительность:**
- ✅ **Плюсы:**
  - НЕТ `spiLock` (не блокирует LoRa radio)
  - Одна операция записи (весь буфер сразу)
  - Прямой доступ к LittleFS (меньше overhead)
  - Оптимизированная проверка flash (2ms вместо ожидания события)
- ⚠️ **Минусы:**
  - Требует RAM буфер (protoSize + 256 bytes)
  - Два этапа: кодирование + запись (вместо одного)
  - Прямые вызовы SoftDevice API (может быть медленнее при активном BLE)

---

## Сравнение производительности

### Запись файла (nodes.proto, ~200 bytes)

**Стандартная FS:**
- Время: ~50-100 ms (оценка)
- RAM: Минимальный (потоковая запись)
- Блокировки: `spiLock` на все время записи
- Операции: Множественные `writecb` вызовы

**Extended FS:**
- Время: ~20-30 секунд (из логов: erase 10s + write 2-3s + sync 10s)
- RAM: ~500 bytes (буфер для protobuf)
- Блокировки: НЕТ `spiLock`
- Операции: Одна операция записи (весь буфер)

### Запись большого файла (nodes.proto, 4KB блок)

**Стандартная FS:**
- Время: ~200-500 ms (оценка)
- Операции: ~4000 вызовов `writecb` (по байту)

**Extended FS:**
- Время: ~20-30 секунд (из логов)
  - Erase: ~10 секунд (1 страница)
  - Write: ~2-3 секунды (1024 слова × 2-3ms на слово)
  - Sync: ~10 секунд (еще 1 страница erase + write)
- Операции: 1 вызов `lfs_file_write()` для всего буфера

## Узкие места Extended Filesystem

### 🔴 КРИТИЧЕСКОЕ: Медленная запись при активном BLE

**Проблема:**
- Запись 4KB блока занимает **2-3 секунды** (1024 слова × 2-3ms на слово)
- Это происходит из-за асинхронных операций SoftDevice
- Каждое слово (4 bytes) требует:
  1. Вызов `sd_flash_write()`
  2. Ожидание события или проверка flash (2ms минимум)
  3. Проверка результата

**Сравнение:**
- Стандартная FS: ~200-500ms для 4KB (через Adafruit wrapper, синхронно)
- Extended FS: ~2-3 секунды для 4KB (через SoftDevice API, асинхронно)

**Причина:**
- SoftDevice API асинхронный (для BLE)
- События могут теряться или задерживаться
- Требуется проверка flash напрямую (2ms на слово)

### ⚠️ ПРОБЛЕМА: Медленное стирание страниц

**Проблема:**
- Стирание 1 страницы (4KB) занимает **~10 секунд**
- Это происходит из-за таймаута 10 секунд перед проверкой flash
- Физическое стирание занимает ~85-100ms, но событие может не прийти

**Сравнение:**
- Стандартная FS: Стирание происходит автоматически через Adafruit wrapper
- Extended FS: Явное стирание через `lfs_erase` callback

### ⚠️ ПРОБЛЕМА: Двойная запись при sync

**Проблема:**
- `lfs_file_sync()` может вызвать еще одну операцию erase + write
- Это добавляет еще ~20 секунд к общему времени записи
- Для файла 200 bytes это избыточно

**Сравнение:**
- Стандартная FS: Sync происходит автоматически при close
- Extended FS: Явный sync может вызвать лишние операции

## Почему Extended FS медленнее?

### 1. Асинхронные операции SoftDevice

**Стандартная FS:**
- Использует синхронный доступ к flash (через Adafruit wrapper)
- Нет ожидания событий SoftDevice
- Быстрая запись (~200-500ms для 4KB)

**Extended FS:**
- Использует асинхронный SoftDevice API
- Требуется ожидание событий или проверка flash
- Медленная запись (~2-3 секунды для 4KB)

### 2. Прямые вызовы LittleFS

**Стандартная FS:**
- Adafruit wrapper оптимизирован для nRF52
- Кэширование и буферизация на уровне wrapper
- Меньше overhead

**Extended FS:**
- Прямые вызовы LittleFS API
- Нет дополнительной оптимизации wrapper
- Больше overhead на каждую операцию

### 3. Дополнительные операции

**Extended FS выполняет:**
- `lfs_remove()` - удаление старого файла
- `lfs_file_open()` - открытие файла
- `malloc()` - выделение буфера
- `pb_encode()` - кодирование в буфер
- `lfs_file_write()` - запись буфера
- `lfs_file_sync()` - синхронизация (может вызвать erase + write)
- `lfs_file_close()` - закрытие файла
- `free()` - освобождение буфера

**Стандартная FS выполняет:**
- `SafeFile()` - открытие (включает remove)
- `pb_encode()` с `writecb` - кодирование + запись одновременно
- `SafeFile::close()` - закрытие (включает sync)

## Что можно оптимизировать?

### ✅ Уже реализовано:

1. **Ранняя проверка flash (2ms):**
   - Сократило время записи с 3.5+ минут до 2-3 секунд
   - Проверка flash после 2ms вместо ожидания события

2. **Увеличенный таймаут (1000ms):**
   - Дает больше времени для SoftDevice при высокой нагрузке

3. **Оптимизированный polling:**
   - Множественные проверки событий в цикле
   - Минимальные задержки

### 💡 Возможные оптимизации:

#### 1. Пакетная запись слов (КРИТИЧНО) ✅ ВОЗМОЖНО!

**Проблема:** Каждое слово пишется отдельно (1024 вызова `sd_flash_write`)

**Решение:** Писать несколько слов за раз (SoftDevice ПОДДЕРЖИВАЕТ!)
- Согласно документации: `sd_flash_write` принимает параметр `size` - количество 32-bit слов
- Максимум: количество слов в одной странице (1024 слова = 4096 bytes)
- Вместо 1024 вызовов по 1 слову → 1-4 вызова по 256-1024 слова
- Сократит количество операций в **256-1024 раза**!
- Ожидаемое улучшение: с 2-3 секунд до **~10-50ms** (улучшение в 40-300 раз!)

**Реализация:**
```cpp
// ТЕКУЩАЯ (медленная):
for (uint32_t i = 0; i < size; i += 4) {
    uint32_t word = *(uint32_t *)((uint8_t *)buffer + i);
    sd_flash_write((uint32_t *)write_addr, &word, 1);  // 1 слово за раз
    // Ожидание события/проверка flash (2ms) × 1024 = 2+ секунды
}

// ОПТИМИЗИРОВАННАЯ (быстрая):
uint32_t words_total = size / 4;  // Количество слов
uint32_t words_per_page = 1024;   // Максимум слов в странице
uint32_t words_written = 0;

while (words_written < words_total) {
    uint32_t words_to_write = (words_total - words_written > words_per_page) 
                             ? words_per_page 
                             : (words_total - words_written);
    
    uint32_t* src_words = (uint32_t*)((uint8_t*)buffer + (words_written * 4));
    uint32_t* dst_addr = (uint32_t*)(write_addr + (words_written * 4));
    
    sd_flash_write(dst_addr, src_words, words_to_write);  // Пакетная запись!
    // Ожидание события/проверка flash (2ms) × 1-4 = 2-8ms вместо 2+ секунд!
    
    words_written += words_to_write;
}
```

**Ограничение:** Нет! SoftDevice API полностью поддерживает пакетную запись до 1024 слов за раз.

#### 2. Кэширование буферов

**Проблема:** `malloc()` и `free()` при каждой записи

**Решение:** Статический буфер для protobuf кодирования
- Избежать выделения/освобождения памяти
- Сократить overhead на ~1-2ms

**Реализация:**
```cpp
static uint8_t encode_buffer[512 * 1024];  // Максимальный размер nodes.proto
// Использовать вместо malloc/free
```

**Ограничение:** Требует RAM (512 KB для максимального размера)

---

#### 3. Оптимизация sync операции

**Проблема:** `lfs_file_sync()` может вызвать лишние erase + write

**Решение:** 
- Проверять, нужен ли sync (если файл маленький, может не требоваться)
- Или использовать `lfs_file_flush()` вместо `sync()` для небольших файлов

**Реализация:**
```cpp
// Для маленьких файлов (< 4KB) использовать flush вместо sync
if (encoded_size < 4096) {
    lfs_file_flush(extended_lfs, &file);  // Быстрее, чем sync
} else {
    lfs_file_sync(extended_lfs, &file);  // Полная синхронизация
}
```

---

#### 4. Отложенная синхронизация

**Проблема:** Sync происходит сразу после записи

**Решение:** Отложить sync до следующей операции или использовать фоновую задачу
- Не блокировать основной поток
- Выполнять sync когда система менее загружена

**Ограничение:** Риск потери данных при сбое до sync

---

#### 5. Использование синхронного режима когда BLE неактивен

**Проблема:** Всегда используется асинхронный режим (даже когда BLE выключен)

**Решение:** Проверять состояние BLE и использовать синхронный режим когда возможно
- Если BLE выключен → использовать прямой доступ к NVMC (быстрее)
- Если BLE включен → использовать SoftDevice API (асинхронно)

**Реализация:**
```cpp
bool use_async = (sd_result == NRF_SUCCESS && sd_enabled);
if (!use_async) {
    // Использовать прямой доступ к NVMC (синхронно, быстрее)
    // Это может быть в 10-20 раз быстрее асинхронного режима
}
```

**Ограничение:** Требует прямой доступ к NVMC регистрам (может конфликтовать с SoftDevice)

---

#### 6. Уменьшение размера блока LittleFS

**Проблема:** Блоки 4KB требуют стирания целой страницы

**Решение:** Использовать меньший размер блока (если возможно)
- Меньше данных для стирания
- Быстрее операции

**Ограничение:** LittleFS требует блоки кратные размеру страницы flash (4KB для nRF52)

## Выводы

### Текущая производительность:

| Операция | Стандартная FS | Extended FS | Разница |
|----------|----------------|-------------|---------|
| Запись 200 bytes | ~50-100 ms | ~20-30 секунд | **200-600x медленнее** |
| Запись 4KB блока | ~200-500 ms | ~2-3 секунды | **4-15x медленнее** |
| Стирание страницы | Автоматически | ~10 секунд | Явное стирание |
| Чтение файла | ~10-50 ms | ~10-50 ms | **Одинаково** |

### Основные причины медленной работы:

1. **Асинхронные операции SoftDevice** - главная причина
   - Каждое слово требует ожидания события или проверки flash (2ms минимум)
   - 1024 слова × 2ms = 2+ секунды минимум

2. **Явное стирание страниц** - дополнительная задержка
   - 10 секунд на каждую страницу
   - Может потребоваться 2-3 страницы для одного файла

3. **Двойная запись при sync** - избыточные операции
   - Sync может вызвать еще одну операцию erase + write

### Рекомендации по оптимизации:

**Приоритет 1 (КРИТИЧНО):**
- ✅ Пакетная запись слов (если SoftDevice поддерживает)
- ✅ Использование синхронного режима когда BLE неактивен

**Приоритет 2 (ВАЖНО):**
- ✅ Оптимизация sync операции (flush для маленьких файлов)
- ✅ Кэширование буферов (статический буфер)

**Приоритет 3 (ОПЦИОНАЛЬНО):**
- ⚠️ Отложенная синхронизация (риск потери данных)
- ⚠️ Уменьшение размера блока (может быть невозможно)

### Ожидаемые улучшения:

После оптимизаций (с пакетной записью):
- **Запись 200 bytes:** с 20-30 секунд до **~50-100ms** (улучшение в **200-600 раз**!)
- **Запись 4KB блока:** с 2-3 секунд до **~10-50ms** (улучшение в **40-300 раз**!)
- **Стирание страницы:** с 10 секунд до **0.1-0.2 секунды** (если использовать синхронный режим)

**КРИТИЧНО:** Пакетная запись - это самая важная оптимизация! Она может сделать Extended FS **быстрее** стандартной FS!

### Итоговая оценка:

**Текущее состояние:** Extended FS работает, но **значительно медленнее** стандартной FS (в 4-600 раз в зависимости от размера файла).

**После оптимизаций (с пакетной записью):** Extended FS может стать **значительно быстрее** стандартной FS:
- Нет `spiLock` (не блокирует LoRa radio)
- Пакетная запись (1-4 операции вместо 1024)
- Прямой доступ к LittleFS (меньше overhead wrapper)
- Ожидаемая скорость: **в 2-10 раз быстрее** стандартной FS для больших файлов!
